Step 0

Prerequisites

Install these tools before cloning the repo. The Wails CLI wraps Go's build system and manages the frontend build pipeline automatically.

1

Go 1.24+

The project's go.mod files require go 1.24.0 or later. Download from go.dev/dl or use brew install go on macOS.

2

Node.js 20+

Required for the Vue 3 / Vite / Vitest frontend toolchain. CI pins to Node 20. Use nvm or download from nodejs.org.

3

Wails CLI v2

The desktop GUI binary is built with Wails v2. Install the CLI once:
go install github.com/wailsapp/wails/v2/cmd/wails@latest
Verify with wails doctor — it checks all platform dependencies.

4

macOS: Xcode Command Line Tools

Required for native macOS builds (WebKit, CGO). Install with: xcode-select --install. For a universal Intel+Apple Silicon bundle, a full Xcode installation is needed.

5

Windows cross-compile: mingw-w64

To build the Windows .exe from macOS (as CI does): brew install mingw-w64. The cross-compiler provides x86_64-w64-mingw32-gcc which Wails uses as the C compiler for CGO.

Verify your setup
$ wails doctor # Wails checks Go, Node, npm, platform WebView, and compiler. # All items must show ✓ before running make run. $ go version go version go1.24.0 darwin/arm64 $ node --version v20.x.x
Structure

Repository Structure

The project contains two independent Go modules that cannot import each other. Changes to shared logic (e.g. tunnel.Manager) must be mirrored in both app/internal/ and app-wails/internal/.

Repository tree
direct-connector/ ├── app/ ← CLI/Docker module (module: mqtt-tunnel) │ ├── internal/ ← config, keygen, p2p, tunnel packages │ ├── cli.go ← CLI entry point (DC_MODE / --mode flag) │ ├── main.go ← GUI entry point (build tag: !nofyne) │ ├── main_nofyne.go ← Headless entry (build tag: nofyne) │ ├── build.sh ← Fyne/CLI build helper │ └── go.mod ← module mqtt-tunnel │ ├── app-wails/ ← GUI module (module: direct-connector) │ ├── app.go ← Wails App struct + all bound methods │ ├── main.go ← Wails bootstrap │ ├── frontend/ ← Vue 3 + TypeScript + Tailwind CSS │ │ ├── src/ │ │ │ ├── components/ ← SshTab.vue, P2pTab.vue │ │ │ ├── test/ ← Vitest tests + setup.ts mock │ │ │ └── utils/ ← portValidation.ts (shared validators) │ │ ├── wailsjs/ ← auto-generated Go bindings (do not edit) │ │ └── package.json │ ├── internal/ ← config, keygen, p2p, relay, sshsetup, tunnel │ └── go.mod ← module direct-connector │ ├── docs/ ← GitHub Pages documentation site ├── Dockerfile ← Static CLI image (CGO_ENABLED=0, nofyne) ├── docker-compose.yml └── Makefile ← Root build targets (make run / test / wails-*)
🔧

Two Go modules

app/go.mod (mqtt-tunnel) owns the Fyne GUI and CLI/Docker binary. app-wails/go.mod (direct-connector) owns the Wails GUI backend. Never import across modules.

🏷️

Build tags (app/ only)

Default (!nofyne) builds the native GUI via main.go. The nofyne tag produces a headless CLI/Docker binary from main_nofyne.go — no OpenGL or X11 dependency.

⚡

Wails bindings

All exported methods on App in app.go become async TypeScript functions. The wailsjs/ folder is auto-generated — never edit it by hand.

Workflow

Development Workflow

The primary development loop uses make run which starts Wails dev mode — a native window with a Vite dev server inside. Go changes trigger a Go rebuild; Vue/TypeScript changes are hot-reloaded via Vite HMR with no restart.

1

Clone the repository

git clone https://github.com/el-j/directConnector.git && cd directConnector

2

Install frontend dependencies

Wails installs them automatically on first make run, but you can also run cd app-wails/frontend && npm install upfront for IDE autocomplete.

3

Start the dev server

make run — opens a native desktop window. Wails proxies the Vite dev server running on port 34115 inside the WebView.

4

Edit Go backend (app.go, internal/)

Save the file. Wails detects the change, rebuilds the Go binary, and relaunches the window automatically.

5

Edit Vue / TypeScript (frontend/src/)

Vite HMR patches the module in-place. No window restart needed — changes appear instantly.

6

Browser DevTools

Open http://localhost:34115 in any browser for the standard Vite dev UI, or right-click inside the Wails window and choose Inspect to access the embedded WebView DevTools.

Common Makefile targets
# Start Wails dev server with hot-reload (primary dev workflow) $ make run # Run all tests in both Go modules + Vitest (see CI) $ make test # Build macOS arm64 bundle → dist/direct-connector-mac.app $ make wails-mac # Build Windows exe → dist/direct-connector-windows.exe # Requires: brew install mingw-w64 $ make wails-windows # Build all platforms (skips missing cross-compilers gracefully) $ make build-all # Remove dist/ and Wails intermediate build output $ make clean
Testing

Running Tests

The project has three test suites: Go backend tests (both modules) and Vitest frontend tests. All three must pass before a PR can be merged — CI enforces this via the test job that blocks both build and pages.

All tests (mirrors CI)

make test
# Runs both Go modules with race detector + Vitest $ make test # Expands to: # cd app-wails && go test -race -count=1 ./... # cd app && go test -race -count=1 ./...

Frontend tests (Vitest)

app-wails/frontend
# Run Vitest once (43 tests across models, SshTab, P2pTab) $ cd app-wails/frontend && npm test # Interactive watch mode (re-runs on file save) $ cd app-wails/frontend && npm run test:watch # TypeScript type-check (no emit) $ cd app-wails/frontend && npx vue-tsc --noEmit

Go tests — granular options

Go test flags
# Run with race detector (required in CI; catches data races) $ go test -race -count=1 ./internal/... # Skip integration tests that require real SSH / network $ go test -short ./internal/... # Run the CLI/Docker module (headless — no Fyne GUI) $ cd app && go test -race -count=1 -tags nofyne ./... # Run a specific package verbosely $ cd app-wails && go test -v -race ./internal/tunnel/...
💡

CI only tests ./internal/... in the Wails module because app-wails/main.go and app.go import the Wails WebView runtime which requires WebKit/GTK headers not present on a stock Ubuntu runner. Local builds on macOS can run ./... without restriction.

CI / CD

CI Pipeline

GitHub Actions runs on every push to main/master, every pull request, and every v* tag. The pipeline has four jobs with explicit dependency edges.

test

Tests — ubuntu-latest · blocks everything

Runs on every push and pull request. All three suites must pass before build or pages can proceed:

  • go test -race -count=1 -v ./internal/... in app-wails/
  • go test -race -count=1 -v -tags nofyne ./... in app/
  • npm ci && npm test (Vitest) in app-wails/frontend/
build

Build — macos-latest (arm64) · needs: test

Runs on every push to default branch and on v* tags. Produces four artifacts uploaded to GitHub Actions:

  • direct-connector-mac.zip — macOS arm64 .app bundle (symlinks preserved)
  • direct-connector-windows.exe — Windows amd64, cross-compiled via mingw-w64
  • direct-connector-cli-darwin-arm64 — headless macOS CLI binary
  • direct-connector-linux-amd64 — headless Linux CLI binary (CGO_ENABLED=0)
pages

Deploy GitHub Pages · needs: test · main/master only

Deploys the docs/ directory to GitHub Pages using the official actions/deploy-pages action. Only runs on pushes to the default branch (never from PRs). Enable in repo Settings → Pages → Source: GitHub Actions.

release

GitHub Release · needs: build · v* tags only

Downloads all four build artifacts and publishes a GitHub Release using softprops/action-gh-release with auto-generated release notes (compiled from merged PRs and commits since the last tag).

Standards

Code Conventions

These patterns are enforced by the existing tests and should be followed in all new code.

Go backend
  • Always use -race flag when writing new tests
  • Mutex naming: mu for the primary lock on any struct
  • Use callback pattern for status/log (OnStatus, OnLog fields) rather than channels, to avoid goroutine leaks
  • String-error return convention: empty string "" means success; non-empty string is the error message — matches Wails TypeScript call sites
  • Table-driven tests with []struct{ name, … } for all new package functions
  • Integration tests that require network should call t.Skip() when testing.Short() is true
TypeScript
  • strict: true in tsconfig.json — no implicit any
  • Use validatePort() / validatePorts() from src/utils/portValidation.ts for all port input fields — never inline parseInt checks
  • String-error convention from Go: check result !== '' for errors from bound methods, not result.ok
  • Model constructors in wailsjs/go/models.ts guard against null/undefined with if (!source) source = {}
Vue components
  • Use v-show, not v-if, to toggle tabs — both tabs must stay mounted so event listeners are active
  • Register all EventsOn listeners in onMounted; call the returned cleanup function in onUnmounted to prevent listener leaks
  • Use <Teleport to="body"> for modals so they render above all other DOM
  • Protect async refresh functions with a refreshing boolean flag to prevent concurrent duplicate calls
Vitest tests
  • Use beforeEach to reset specific mocks — do not use vi.resetAllMocks() globally as it clears the Wails runtime shim
  • Use globalThis.__testEmitEvent(eventName, payload) to simulate backend events (tunnel:status, setup:prompt, etc.) in component tests
  • Call await flushPromises() after actions that trigger async Go method calls before asserting DOM state
  • Log arrays: test that they cap at 200 lines, not that they contain specific indices
Extending

Adding a New Backend Method

All exported methods on the App struct in app-wails/app.go automatically become async TypeScript functions via Wails bindings. Follow this checklist when adding a new one.

1

Add the method to app.go

Define the exported method on *App. Use the string-error return convention: return "" on success and a non-empty error string on failure. For long-running operations, accept a context or use runtime.EventsEmit to push progress events.

2

Regenerate Wails bindings

cd app-wails && wails generate module — regenerates frontend/wailsjs/go/main/App.js and App.d.ts to include the new method.

3

Verify the TypeScript declaration

Open frontend/wailsjs/go/main/App.d.ts and confirm your method appears with the correct parameter and return types. Fix the generated declaration if Wails inferred an any type incorrectly.

4

Update the test mock in setup.ts

Add a vi.fn() stub for the new method in frontend/src/test/setup.ts. The mock is referenced by the Vitest auto-mock for wailsjs/go/main/App so component tests don't call real Go code.

5

Write component and unit tests

Add tests in the relevant *.test.ts file covering the happy path, error path (non-empty string return), and any emitted events the method produces.

6

Update docs/api.html

Document the method signature, parameters, return value, and any events it emits in the API Reference page so users of the TypeScript bindings understand the contract.

Example — adding MyNewMethod to app.go
// app-wails/app.go // MyNewMethod does X. Returns "" on success, error string on failure. func (a *App) MyNewMethod(param string) string { a.mu.Lock() defer a.mu.Unlock() // ... implementation ... return "" // success } // Regenerate bindings: $ cd app-wails && wails generate module // frontend/src/test/setup.ts — add mock: MyNewMethod: vi.fn().mockResolvedValue('')
Extending

Adding a New Internal Package

Both modules have parallel internal/ directories. If the new package is needed only by the Wails GUI, add it to app-wails/internal/. If it's also needed by the CLI/Docker module, mirror it in app/internal/ as well.

1

Create the package directory

Under app-wails/internal/<pkgname>/ (and optionally app/internal/<pkgname>/). Use lowercase, single-word package names matching the directory name.

2

Define a clean public API

Export only what app.go (or main.go) needs. Keep internal types unexported. Use callback fields (OnStatus func(…)) rather than channels for async notification.

3

Write table-driven unit tests

Create <pkgname>_test.go with package <pkgname>_test (black-box style). Use t.TempDir() for file I/O. Mark slow network tests with if testing.Short() { t.Skip() }.

4

Wire the package into app.go

Import the package and add any required fields to the App struct. Initialize in NewApp() and clean up in the shutdown lifecycle method if the package owns goroutines.

5

Mirror in app/internal/ if needed by CLI

The two modules cannot share code at the Go module level. If the CLI Docker image needs the same functionality, duplicate the package (keeping both in sync manually or via a script).

📦

Existing packages for reference: internal/config (JSON config), internal/keygen (Ed25519 keypair), internal/tunnel (SSH subprocess), internal/p2p (WebRTC), internal/relay (embedded TURN server), internal/sshsetup (interactive key installer, Wails module only).

Pull Requests

Pull Request Checklist

Run through this checklist before opening a PR. CI will catch most failures, but checking locally first avoids wasted CI minutes.

All tests pass: make test (Go — both modules, with -race) and cd app-wails/frontend && npm test (Vitest)
TypeScript is clean: cd app-wails/frontend && npx vue-tsc --noEmit exits with no errors
No new dependencies added without a security scan. Check GitHub Advisory Database for known CVEs in any new package
If the change resolves or adds a known issue, update the todo list in docs/audit.md accordingly
If new App methods were added, docs/api.html has been updated with method signatures, parameters, and emitted events
Port validation uses validatePort() / validatePorts() from src/utils/portValidation.ts — no inline range checks
Vue components using EventsOn call the returned cleanup function in onUnmounted
If the legacy app/ module is affected, changes are mirrored in app/internal/ alongside app-wails/internal/
Releases

Release Process

Releases are fully automated — pushing a semver tag is the only manual step required. The CI pipeline handles building, packaging, and publishing.

1

Merge all changes to main

Ensure make test passes cleanly on the default branch before tagging. The pages job will deploy the latest docs automatically.

2

Push a semver tag

Tags matching v* (e.g. v1.2.3, v2.0.0-rc1) trigger the full CI pipeline. Use annotated tags: git tag -a v1.2.3 -m "v1.2.3" && git push origin v1.2.3

3

CI builds four artifacts on macOS arm64

The build job produces: direct-connector-mac.zip (macOS .app bundle), direct-connector-windows.exe (cross-compiled via mingw-w64), direct-connector-cli-darwin-arm64 and direct-connector-linux-amd64 (headless CLI binaries).

4

GitHub Release is published automatically

The release job downloads all four artifacts and creates a GitHub Release at github.com/el-j/directConnector/releases using softprops/action-gh-release with auto-generated release notes compiled from merged PRs and commits since the previous tag.

5

Download buttons update automatically

The landing page (docs/index.html) fetches the latest release from the GitHub API at load time — no manual update needed. Users always see the newest version.

Tagging a release
# Ensure main is green and up to date $ git checkout main && git pull $ make test ✅ All tests passed. # Create and push an annotated semver tag $ git tag -a v1.2.3 -m "v1.2.3" $ git push origin v1.2.3 # CI triggers: test → build → release # Release is published at: # https://github.com/el-j/directConnector/releases/tag/v1.2.3
⚠️

The release job requires contents: write permission. This is declared in the workflow and granted automatically by GitHub Actions for pushes from the repository owner. Fork contributors cannot trigger releases directly — they open PRs which are merged and tagged by a maintainer.
