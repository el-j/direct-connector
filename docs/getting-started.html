Getting Started

Get started in minutes.

Direct Connector gives you encrypted reverse SSH tunnels and serverless WebRTC peer-to-peer connections — no cloud subscription, no relay, no third party. This guide walks you from download to your first live tunnel in under five minutes.

Before you begin

Prerequisites

Direct Connector is lightweight and has almost no external dependencies. What you need depends on which tunnel mode you plan to use.

🖥️

Supported platforms

macOS arm64 (Apple Silicon, macOS 12+) or Windows 10 / 11 x64 for the GUI desktop app. Linux users can run the headless CLI binary or Docker image on any amd64 system.

🔐

For SSH Tunnel mode

An SSH jump server you control — a VPS, cloud instance, or any machine reachable from the internet on port 443 (or your chosen port). You need a login with permission to edit ~/.ssh/authorized_keys.

🌐

For P2P mode

Any two machines with internet access. No server, no account, no firewall rules needed. For symmetric NAT or CGNAT networks an optional TURN relay URL can be supplied, but the vast majority of connections succeed without one.

Step 0

Download & Install

The desktop app is a single self-contained binary — no installer, no runtime, no system libraries. Pick the build for your platform below.

①

macOS (Apple Silicon)

Download direct-connector-mac.zip from the latest release. Unzip it (double-click or unzip direct-connector-mac.zip), then drag Direct Connector.app into your Applications folder, or simply double-click to run it from Downloads.

⚠️
macOS Gatekeeper

Because the app is not yet notarized by Apple, macOS will block it on first launch. To bypass this: right-click (or Control-click) the app icon → choose Open → click Open in the dialog. You only need to do this once.

②

Windows (x64)

Download direct-connector-windows.exe from the latest release. No installer is needed — just run the .exe directly. Windows may show a SmartScreen warning on first launch because the binary is unsigned; click More info → Run anyway to proceed.

③

Linux (headless CLI or Docker)

The Linux build is a headless CLI binary — no GUI, no OpenGL dependency. Download direct-connector-linux-amd64, mark it executable, and run it from a terminal. Alternatively, pull the Docker image for zero-install deployment. See the CLI & Docker section below for full details. 

$ chmod +x direct-connector-linux-amd64
$ ./direct-connector-linux-amd64 --help
Orientation

First Launch

When you open Direct Connector for the first time, the app loads directly into the SSH Tunnel tab. The window is split into two tabs along the top, one for each tunnel mode, and a real-time log panel runs along the bottom of each tab to display connection events.

On macOS and Windows a system tray / menu-bar icon appears immediately. You can minimize the window and the tunnel stays active in the background — use the tray icon to bring it back or quit the app entirely.

Your configuration is stored in a JSON file at the OS-standard user config directory (~/Library/Application Support/MQTTTunnelManager/ on macOS, %AppData%\MQTTTunnelManager\ on Windows). The app writes a new config snapshot every time you successfully start a tunnel, so your settings are never lost across restarts.

The Ed25519 key pair used for passwordless SSH is generated once and stored alongside the config file. The public key is what gets installed on your server; the private key never leaves your machine.

💡
Two tabs, one app

SSH Tunnel creates a persistent reverse tunnel through a jump server you control. P2P Tunnel establishes a direct, serverless connection between two machines using WebRTC. Both tabs stay mounted while the app is running so you can switch modes instantly without losing state.

Tunnel mode 1

SSH Tunnel Quickstart

An SSH reverse tunnel punches an encrypted connection from your local machine out to a jump server, then forwards one or more ports back. Port 443 is the default because it passes through virtually every corporate firewall and proxy.

1

Enter your server details

In the SSH Tunnel tab, fill in:

Host — the hostname or IP of your jump server (e.g. jump.example.com)
Port — leave at 443 unless your SSH daemon listens elsewhere
Username — the Linux user on the jump server (e.g. admin or ubuntu)
Remote ports — comma-separated list of ports to forward (e.g. 1883,3391)

💡

Using port 443 for SSH requires adding Port 443 (or a second ListenAddress line) to /etc/ssh/sshd_config on the server, then restarting sshd. If your server already runs HTTPS on 443 you can use sslh to multiplex both on the same port.

2

Generate (or import) your app key

Click Generate Key to create a fresh Ed25519 key pair stored in the app's config directory. If you already have an existing private key you prefer, click Use existing key and browse to the file — the app copies it into its config directory so the original is never touched.

The public key is shown as a one-line string in the text box. You can copy it manually and append it to ~/.ssh/authorized_keys on the server, or let the app do it automatically in the next step.

3

Install key on server — one-time password entry

Click Install Key on Server. The app dials the server over SSH, shows the server's host fingerprint for verification, then prompts for your password. After you confirm, it appends the public key to ~/.ssh/authorized_keys on the server.

You only enter your password once. Every subsequent connection uses the key pair — no password is ever stored by the app.

🔑
Auth check

After installation, click Check Key Auth to verify that the server accepts your key before attempting the tunnel. A green tick means you're ready.

4

Start the tunnel

Click Start Tunnel. The log panel at the bottom of the tab will fill with output from the SSH process. A successful connection looks like:

tunnel log
# app log output 2024/01/15 12:34:01 tunnel: starting ssh -N -R 1883:localhost:1883 admin@jump.example.com -p 443 2024/01/15 12:34:02 tunnel: connected 2024/01/15 12:34:02 tunnel: forwarding ports [1883]

The tunnel auto-reconnects within five seconds if the connection drops — from network changes, sleep, or a server restart. The status indicator in the tab header turns green when the tunnel is live.

5

Verify end-to-end connectivity

From any machine that can reach your jump server, test that the forwarded port is reachable. For an MQTT broker on port 1883:

remote machine
# subscribe on the remote machine via the tunnel $ mosquitto_sub -h jump.example.com -p 1883 -t test/#   # or verify the port is open with netcat $ nc -zv jump.example.com 1883 Connection to jump.example.com 1883 port [tcp/*] succeeded!
Troubleshooting

Common errors & fixes

Permission denied (publickey)

The public key was not installed or the server's AuthorizedKeysFile path differs from the default. Re-run Install Key on Server, or manually append the public key to ~/.ssh/authorized_keys with correct chmod 600 ~/.ssh/authorized_keys permissions.

ssh: connect to host … port 443: Connection refused

The server's sshd is not listening on port 443. Add Port 443 to /etc/ssh/sshd_config and restart sshd with sudo systemctl restart sshd. Ensure port 443 is open in the server's firewall / security group.

Warning: remote port forwarding failed for listen port …

Another process is already listening on that port on the server, or GatewayPorts yes is not set in sshd_config. Add GatewayPorts yes and restart sshd, or choose a different remote port.

Host key verification failed

The server's fingerprint changed (possibly a reinstall). Remove the old entry from ~/.ssh/known_hosts with ssh-keygen -R [host]:443, then reconnect and confirm the new fingerprint.

Tunnel mode 2

P2P Tunnel Quickstart

The P2P mode uses WebRTC DataChannels to punch a direct, encrypted tunnel between two machines — the same technology behind browser video calls. The only exchange needed is a short base64 text blob copied between machines; no server relays your data.

ℹ️
Roles: Consumer & Provider

Consumer is the machine that wants to use a service (e.g. subscribe to MQTT). Provider is the machine that hosts the service (e.g. runs the broker). Either machine can be behind NAT — both just need outbound internet access.

Consumer (machine A)

Generate the Offer

1

Open the P2P Tunnel tab. Enter the local port(s) you want forwarded — e.g. 1883 for MQTT.

2

Click Generate Offer. The app performs ICE candidate gathering and produces a base64 blob in the text area. This takes a few seconds.

3

Copy the entire base64 blob and send it to the Provider (e.g. via chat, email, or any channel).

4

Wait for the Provider to send back an answer blob, paste it into the answer text area, then click Connect.

Provider (machine B)

Accept & Generate Answer

1

Open the P2P Tunnel tab on the Provider machine and switch to the Provider sub-mode.

2

Paste the Consumer's offer blob into the offer text area.

3

Click Accept & Generate Answer. The app produces its own base64 answer blob.

4

Copy the answer blob and send it back to the Consumer. Once the Consumer pastes it and clicks Connect, the tunnel goes live on both sides.

🔄
Symmetric NAT / CGNAT

If ICE negotiation fails (both machines are behind carrier-grade NAT or symmetric NAT), provide a TURN relay URL in the advanced settings of the P2P tab. The TURN server only relays the connection — it does not see your tunnel's payload, which remains DTLS 1.2 encrypted end-to-end. Free TURN servers such as Open Relay work fine for low-bandwidth tunnels.

Headless & server deployments

CLI & Docker Quickstart

For server automation, CI pipelines, or embedded Linux systems, Direct Connector ships a headless CLI binary compiled with no GUI dependency. Every flag has an equivalent DC_* environment variable, making pure-env Docker configuration straightforward.

1

Download the CLI binary

Grab direct-connector-linux-amd64 from the latest release, or pull the Docker image:

# native binary $ curl -LO https://github.com/el-j/directConnector/releases/latest/download/direct-connector-linux-amd64 $ chmod +x direct-connector-linux-amd64   # or pull the Docker image $ docker pull ghcr.io/el-j/direct-connector:latest
2

SSH tunnel mode

All flags map 1-to-1 to DC_-prefixed environment variables. Supply a pre-installed private key via --key or mount it as a Docker secret:

# native CLI — SSH tunnel $ ./direct-connector-linux-amd64 \ --mode ssh \ --host jump.example.com \ --port 443 \ --user admin \ --ports 1883,3391 \ --key /config/id_ed25519   ✓ tunnel connected — forwarding 1883,3391
3

P2P mode (file-based SDP exchange)

In automated or headless environments, the CLI reads the offer blob from a file and writes the answer blob to a file, making it composable with scripts:

# Consumer: generate offer to file $ ./direct-connector-linux-amd64 \ --mode p2p-consumer \ --offer-out /data/offer.txt \ --answer-in /data/answer.txt \ --ports 1883   # Provider: read offer, write answer $ ./direct-connector-linux-amd64 \ --mode p2p-provider \ --offer-in /data/offer.txt \ --answer-out /data/answer.txt
4

Docker Compose one-liner

The Docker image accepts all configuration via environment variables, making it ideal for docker-compose.yml or Kubernetes manifests. Mount a named volume for the SSH key so it persists across container restarts:

# docker-compose.yml snippet services: tunnel: image: ghcr.io/el-j/direct-connector:latest environment: DC_MODE: ssh DC_HOST: jump.example.com DC_PORT: "443" DC_USER: admin DC_PORTS: "1883,3391" volumes: - dc-config:/config restart: unless-stopped   volumes: dc-config:   # bring it up $ docker compose up -d ✓ tunnel connected — forwarding 1883,3391
